# 管理者の復旧: 未実装の設計

通常のメール復旧では管理者を復旧できない。すべてのパスキーを失った場合も、メールの支配だけで管理権限を得られないよう、GitHub の運用権限と登録済みメールの確認を別々に必要とする。

1. 運用者が本人確認を行い、管理者設定時のコードを指定して復旧を開始する。対象が現在の唯一の管理者であることを確認し、短期間のみ有効な1回限りの確認リンクを登録済みメールへ送る。この段階では管理者権限やパスキーを変更しない。
2. メールの所有者がリンク先で明示的に確認する。メールの自動スキャナーがリンクを開いただけでは完了させない。確認トークンはハッシュで保存し、期限、回数制限、再送時の無効化を設ける。
3. 運用者が確認済みで期限内の対象を再確認してから、明示的な操作を行う。古いパスキー、セッション、未完了の復旧を失効し、管理者権限を外す操作は単一 D1 トランザクションとする。古いログイン処理の完了を防ぐため認証世代も更新し、セキュリティ通知を同じトランザクションに積む。お気に入りと再生履歴は変更しない。
4. 本人が通常のメール復旧で新しいパスキーを登録し、別の保存先にも予備を追加する。運用者が再びコードを照合し、初期管理者の設定手順で権限を戻す。確認メールの実配送、メール不達時の再試行、権限復帰までを実機で確認する。

確認リンク用の状態保存、配送の失敗・再試行、期限切れ削除、途中中断からの再開、対象の再照合、他アカウントとの競合は実装と試験が必要。メールの暗号化鍵や送信設定が壊れている場合に、確認前の古い認証情報を消してはならない。この設計は未実装であり、本番フラグを有効化する理由にはならない。
