# 確認方針

本番の認証を無効のまま、分離されたテスト環境または使い捨て D1 を使う。実在のアドレスや認証情報をログに出さない。データの消去と書き込み順序の保証が衝突する箇所は、単純な削除を採用せず、遅延リクエストを拒否する設計と併せて解決する。

管理者はメールによる通常の復旧の対象外。運用者による本人確認と安全な権限の設定・復旧手順を、公開前に別途確定する。

登録・復旧の開始は宛先の入力検証と回数制限を行ってから共通の応答を返す。アカウント照合とメール配送は Worker の `waitUntil` で応答後に実行し、配送の有無によって API が処理を待つ時間を変えない。処理の失敗は個人情報を含めず記録する。これだけで全ての時間差攻撃を防げるという保証はなく、独立レビューと実環境での確認が必要。

## 履歴の削除と遅延書き込み

履歴消去の際にカーソルを単純に消すと、消去前の遅延した再生位置リクエストが後から届いたとき、古い再生履歴を再作成しうる。対応候補として、アカウントごとの履歴世代を持ち、履歴消去を「世代を進める・履歴を消す・カーソルを消す」単一トランザクションにする。再生位置の更新は、クライアントが持つ世代が現在と一致することを同じトランザクション内で確かめる。読み出しも履歴と世代を一貫したスナップショットで返す。

この方式を `0018_history_generations.sql` とアカウント API に実装する。移行・古いクライアント・別タブで再生中の場合の再同期と、消去と更新の前後関係を変えた試験が必要。過去の履歴を削除しても、消去後の新たな再生は履歴に記録される。
