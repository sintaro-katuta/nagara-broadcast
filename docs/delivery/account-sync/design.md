# 設計（実装中）

Google・AppleのOAuth処理は撤去する。WebAuthnの検証にはSimpleWebAuthnを使用し、HTTPSのoriginとRP ID、ユーザー確認を必須にする。サーバーで発行するチャレンジは5分で期限切れ、一度だけ消費する。登録を認証済みセッションまたは確認済み登録・復旧処理に結び付け、第三者によるパスキー追加を防ぐ。

D1にはランダムな内部ユーザーID、公開鍵・認証情報ID・署名カウンター、お気に入り・履歴、セッションのハッシュを保存する。端末の秘密鍵や生体情報は受け取らない。メールアドレスはAES-GCMで暗号化し、別鍵のHMACで検索する。鍵はD1とは別にWorker secretsとして管理し、紛失時の復旧とローテーションを公開前に設計・検証する。メール送信時には配信事業者にもアドレスが渡る。

`passkey-login.mjs` はブラウザ固有の短命Cookieに紐づくチャレンジを一度だけ消費して署名を検証し、成功時にセッションを発行する内部ハンドラー。署名カウンターは比較更新する。公開ルートには接続していない。`recovery-tokens.mjs` は256ビットの乱数をハッシュ化して保存し、用途ごとに15分間のみ一度だけ受け付ける内部部品。`auth-rate-limit.mjs` は接続元等をHMAC化し固定時間枠で回数を数える内部部品であり、まだAPIに組み込まれていない。

`passkey-registration.mjs` は既存セッションに紐付く追加パスキー登録の内部ハンドラー。登録開始と完了が同じアカウント・同じブラウザで行われることを確認する。本人の直近の再認証や通知は未実装であり、公開ルートには接続していない。新規登録やメール復旧には使用できない。

`passkey-enrollment.mjs` は新規登録の内部サービス。仮登録には暗号化したメールアドレスと確認トークンのハッシュを保存し、確認後はブラウザ用トークンのハッシュに切り替える。正しいパスキー登録の検証に成功してから、アカウント・確認済みアドレス・公開鍵をD1のバッチで確定する。使用済みの確認トークンと登録チャレンジは再利用できない。登録失敗時はやり直しとなる。`enrollment-email.mjs` はCloudflare Email Serviceの送信形式でメールを用意し、確認トークンはHTTPリクエストに含まれないURL fragmentに置く。確認の消費はリンクを開いただけでなく明示的なPOSTで行う必要がある。

`passkey-recovery.mjs` は確認済みメール宛の復旧トークンと、ブラウザに紐付いた一度限りのパスキー登録を扱う内部サービス。復旧トークンの消費とブラウザへの復旧権限の移行はD1の一つのトランザクションで行う。新規登録と復旧のチャレンジはそれぞれ最大5分で失効し、ブラウザ操作の有効期間を超えない。復旧成功時には他の復旧トークン・進行中の復旧・既存セッションを無効化し、新しいパスキーとセッションを同じD1トランザクションで発行する。アカウントの認証世代を更新し、それより前に開始された通常ログインが後からセッションを発行しないようにする。新規登録のセッションもアカウント作成と同一トランザクションで保存する。既存のパスキーは削除しない。管理者はメール復旧の対象外。既存パスキーが20個の場合の復旧方法は未完成。

`auth-routes.mjs` は登録・ログイン・復旧の内部処理をHTTPに接続し、同一オリジン、短命のHttpOnly Cookie、接続元とメール宛先の回数制限を適用する。メール送信はCloudflare Email Serviceのbindingを利用する。Workerでは `AUTH_ENABLED` と `PASSKEY_API_ENABLED` がともに明示的に `true` の場合だけ処理する。

`public/account-ui.js` は登録・ログイン・メール復旧画面を提供し、URL fragmentのトークンをメモリだけで保持して即座に履歴から除去し、利用者の明示操作後に確認APIへ送る。確認・パスキー登録途中の画面は閉じても同じタブ内では再開できる。認証が設定されていない場合は従来の「準備中」を表示する。公開版のお気に入りと再生履歴は認証セッションに紐付けてD1と同期し、ログアウト・セッション失効時にはブラウザメモリから消す。ローカル版は従来どおりブラウザ内に保存する。

ブラウザのタブ間通知と復帰時の再読込に加え、書き込みとログアウト時には取得時のセッション識別子をサーバー側で照合する。これにより別タブでアカウントが変わっても旧画面の操作を別アカウントに適用しない。再生開始時はメタデータを確認し保存位置を復元してから同期する。画面終了時はkeepalive付きリクエストを直ちに送信し、同一画面からの遅延更新に上書きされないようD1にページごとの順序を記録する。keepaliveは端末やネットワークによる配送を保証しない。

通常の再生位置更新も直ちに送信し、同じページからの順序逆転はD1で拒否する。先行する通信の完了やアカウント情報の再取得を待たないため、同じセッションの再照会で一時停止位置を破棄しない。各通信は開始時のセッション識別子で検証する。

セッション再照会中の再生位置保存には、直前のセッション識別子を使用する。サーバーは現在のCookieと照合し、別アカウントに変わっていた場合は保存を拒否する。アカウント情報の取得と同じセッションの位置保存が重なる場合、保存の完了を待ってから再取得する。取得開始前から保存中の場合や取得中に保存が始まった場合も、古い履歴を画面へ渡さない。

メール送信先の本番設定、再生位置の順序管理カーソルの清掃、パスキーの管理・失効、アカウント削除、管理者復旧、実運用に適したレート制限・アカウント列挙対策は未完成。復旧完了の通知待ちと再送は実装したが、実配送・バウンスと滞留の運用確認が必要。期限切れの一時認証データの清掃は実装したが既定では無効であり、実D1での検証が必要。実ブラウザ・複数端末・メール配送の検証も必要。両方の認証フラグは有効化してはならない。

保存容量集計は登録済み音声のサイズの合計であり、R2全体や請求対象容量ではない。履歴の取得は最新200件で、自動削除ではない。
# 初期再生とアカウント情報

公開版ではアカウント状態と履歴が確定するまで、再生開始時の位置復元と位置保存を保留する。音声の準備とアカウント情報はどちらが先に完了してもよく、両方が揃った時点で保存済み位置を復元する。未ログインや認証機能が無効と確認できた場合は先頭から再生する。通信エラーでは状態が確定しないため、保存済み位置をゼロで上書きしない。

初期照会の失敗後は通信復帰・画面復帰・アカウント画面を開く操作で再試行し、同時の初期照会はまとめる。お気に入りの保存完了後はアカウント情報を再取得し、それ以前に始まった古い照会結果を破棄する。
